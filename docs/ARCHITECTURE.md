# XLaunch 整体架构

## 1. 架构目标

XLaunch 采用单进程、原生桌面应用架构。设计重点是缩短启动路径、限制资源占用、保持配置易编辑，并让 Win32、渲染、界面和核心数据之间的边界足够清楚。

架构保持扁平：不引入服务容器、事件总线、脚本系统、插件框架或复杂领域层。只有当实际需求出现并能降低维护成本时，才增加抽象。

## 2. 当前工程基线

当前目录是 Visual Studio 2026 创建的 Win32 桌面应用模板：

- `XLaunch.cpp` 包含 `wWinMain`、窗口注册、消息循环和模板菜单处理。
- `XLaunch.rc`、`Resource.h` 和图标文件提供 Win32 资源。
- `XLaunch.vcxproj` 使用 v145 工具集，当前语言标准为 C++20。
- 工程包含 Win32/x64 和 Debug/Release 配置。
- 已固定引入 Dear ImGui v1.92.5，并使用其官方 Win32/DX11 后端。
- 已建立 DirectX 11 设备、交换链与渲染循环。
- 已固定引入 nlohmann/json v3.12.0，并限制在 `ConfigManager.cpp` 使用。
- 当前目录已初始化 Git，但尚无提交。

资源文件保持原有结构；入口代码已在阶段 1 替换为最小 Win32/DX11/ImGui 外壳。模块化迁移将在后续阶段按实际需要增量进行。

`PortablePath` 以 EXE 目录为绿色版根目录：保存时仅将根目录内的本地路径转为相对路径，启动、图标提取和打开所在位置前再解析为绝对路径。外部目标和 URL 保持原值。

主窗口使用 Per-Monitor DPI awareness，处理 `WM_DPICHANGED` 的新 DPI 和 Windows 建议窗口范围，然后重新应用 ImGui 样式、字体比例和主网格尺寸。

## 3. 目标模块

### app：应用生命周期与编排

负责启动顺序、关闭顺序、模块所有权和每帧协调。它是组合各模块的唯一位置，不包含具体界面绘制、JSON 细节或 Shell 调用实现。

建议对象：`Application`。

### core：核心数据与用例

保存不依赖 Win32、ImGui 和 DX11 的数据模型及操作规则，例如：

- `Category`：分类标识、名称和排序
- `LaunchItem`：名称、目标、参数、工作目录和图标来源
- `LauncherModel`：分类集合、当前选择和启动项集合

核心层负责数据一致性，但不直接读写文件、不绘制界面、不调用系统启动 API。

### config：JSON 配置持久化

负责配置路径、JSON 解析、字段校验、默认值、版本兼容和安全保存。对外提供明确的加载/保存结果，不把 nlohmann/json 类型泄漏到其他模块。

配置位于 `XLaunch.exe` 同目录的 `config\xlaunch.json`，以绿色软件方式随程序目录移动。保存时先写入同目录临时文件，成功后使用 Windows 原子替换正式文件，避免中途失败破坏已有配置。新路径首次启动时会从旧的 LocalAppData 路径执行一次性安全复制迁移。

### platform：Windows 平台能力

集中封装 Windows 专属操作：

- Win32 窗口创建与消息处理
- 使用 Shell 启动程序、文件或目录
- DPI 和显示器信息
- 文件对话框、拖放等后续经确认的能力
- 系统图标提取和路径处理
- OLE `IDropTarget`、`CF_HDROP` 多路径接收和启动项目默认字段解析

该层返回普通 C++ 数据或明确的结果类型，避免 Windows 句柄扩散到核心层。

### renderer：DX11 与 ImGui 渲染基础设施

负责 D3D11 设备、交换链、渲染目标和 ImGui 后端生命周期，包括窗口尺寸变化和设备异常处理。它不决定界面内容，也不持有分类或启动项业务数据。

`IconCache` 按启动项目 ID 缓存 DX11 Shader Resource View。签名包含目标路径、自定义图标路径、项目类型和像素尺寸；签名变化时替换纹理，项目删除时清理无效缓存，应用关闭时统一释放全部 COM 资源。

### ui：界面与交互

使用 Dear ImGui 绘制固定布局：顶部横向分类栏和主区域图标网格。应用内编辑界面也属于该模块。

UI 读取核心模型并产生清晰的用户意图，例如选择分类、请求启动、编辑或排序；实际 Shell 调用和配置写入由相应模块完成。

### tests：纯逻辑验证

`ConfigManagerTests` 覆盖项目增删改、复制、移动、分类与外观设置的保存/重载，以及临时文件清理。渲染及 Win32 行为以针对性的启动检查为主，不引入第三方测试框架。

## 4. 依赖方向

```text
Win32 entry point
        |
        v
      app -------------------------------+
       |                                  |
       +--> ui ------> core               |
       |     |                            |
       |     +-------> renderer           |
       |                                  |
       +--> config ---> core              |
       |                                  |
       +--> platform ---------------------+

core 不依赖 Win32、ImGui、DX11 或 JSON。
ui 不直接读写配置文件，也不直接执行 Shell 启动。
renderer 不依赖 core 或 config。
```

第三方库的使用范围也应受限：Dear ImGui 只出现在 UI/渲染边界，nlohmann/json 只出现在 config，DX11 只出现在 renderer 和必要的平台接合处。

## 5. 运行流程

### 启动

1. `wWinMain` 创建 `Application`。
2. 平台层创建 Win32 窗口。
3. 渲染层初始化 DX11 和 ImGui 后端。
4. 配置层定位、读取并校验 JSON。
5. 核心模型接收有效配置；失败时使用可恢复的最小状态并报告原因。
6. 进入消息与渲染循环。

启动路径不执行网络请求，不扫描磁盘，不预加载所有系统资源。图标等相对昂贵的数据应按需加载，并设置明确缓存上限。

### 每帧

1. 处理 Win32 消息。
2. 开始 ImGui 帧。
3. UI 绘制分类栏和当前分类的图标网格。
4. `Application` 处理 UI 产生的意图。
5. 渲染层提交并呈现画面。

无交互时避免后台轮询和无意义工作；是否采用持续渲染或按需唤醒，应在阶段 1 用实际资源数据决定。

### 启动项目

1. UI 产生包含启动项标识的启动请求。
2. 应用层从核心模型取得经过校验的启动信息。
3. 平台层调用 Windows Shell。
4. 结果返回 UI，以简洁方式展示失败信息。

### 关闭

按 UI、配置、渲染、窗口的明确顺序释放资源。只有发生配置变更时才保存，避免每帧或无变化写盘。

## 6. 配置原则

当前配置版本为 2，启动项目保存自动名称、自定义名称、目标、参数、工作目录、自定义图标、管理员标记、项目类型和排序值：

```json
{
  "version": 1,
  "categories": [
    {
      "id": "work",
      "name": "工作",
      "items": [
        {
          "id": "item-1",
          "automaticName": "App.exe",
          "customName": "示例程序",
          "target": "C:\\Path\\App.exe",
          "arguments": "",
          "workingDirectory": "",
          "customIconPath": "",
          "runAsAdministrator": false,
          "type": "exe",
          "sortOrder": 0
        }
      ]
    }
  ]
}
```

不在 JSON 中保存运行期句柄、纹理、派生缓存或机器无关的临时 UI 状态。

配置解析失败后不会立即写回。若用户随后产生配置变更，保存前必须先成功创建带时间戳的 `.corrupt-*` 原文件备份；备份失败则拒绝覆盖。

## 7. 图标解析

- 自定义图标路径拥有最高优先级。
- exe 和自定义图标通过 Shell 图标资源提取。
- lnk 使用 `IShellLinkW`/`IPersistFile` 解析目标及图标位置。
- 普通文件和文件夹通过 `SHGetFileInfoW` 获取系统关联图标。
- URL 优先使用默认浏览器可执行文件图标。
- 所有路径失败时使用统一的 Windows 应用程序备用图标。
- `HICON` 绘制到 32 位 DIB 后上传为不可变 DX11 BGRA 纹理，上传完成即释放 GDI 图标和位图资源。

## 8. 文件拖入

- 主窗口通过 `RegisterDragDrop` 注册轻量 `IDropTarget`，不创建额外窗口。
- `DragEnter`/`DragLeave` 只更新拖入视觉状态，`Drop` 一次读取全部 `CF_HDROP` 路径。
- `LaunchItemFactory` 是拖放与文件/文件夹浏览的共同解析入口。
- exe 读取版本资源中的 `FileDescription`，失败后使用无扩展名文件名。
- lnk 通过 `IShellLinkW` 读取真实目标、参数、工作目录和图标位置；解析失败会显示错误。
- url 读取 `[InternetShortcut]` 中的 URL 和图标路径。
- 解析成功的非重复项目批量加入当前分类并立即安全保存；重复项目逐个确认。

## 9. 全局呼出、自启与备份

- `HotkeyManager` 对用户录制的修饰键与虚拟键组合使用 `RegisterHotKey`；仅在选择鼠标中键时安装 `WH_MOUSE_LL`，不使用后台轮询。录制期间先释放旧快捷键，完成或取消后重新注册。
- 快捷触发在窗口位于前台时隐藏窗口；窗口隐藏、最小化或位于后台时恢复并带到前台。
- `StartupManager` 只管理 `HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run` 下的 XLaunch 值，不需要管理员权限。
- `BackupManager` 负责原配置复制、导入/导出文件选择和自动备份轮换。导入文件先由 `ConfigManager` 完整解析，通过后才提交到当前配置。
- 自动备份位于配置目录的 `backups` 子目录，配置保存后按最短时间间隔生成，并按用户设置的数量删除最旧文件。
- `TrayIconManager` 使用 `Shell_NotifyIconW` 管理唯一托盘图标。普通关闭只隐藏主窗口，托盘“退出”、系统会话结束才进入完整清理流程。
- 托盘菜单只包含显示/隐藏、作者主页和退出；作者主页通过系统默认浏览器打开。
- 鼠标手势由低级钩子维护中键、侧键 1/2 的按下状态与双击时间，可组合“按住键 + 主键”或主键双击。
- 进程使用命名互斥保证单实例；后续实例向既有窗口发送显示消息后立即退出。
- 主窗口隐藏时主循环进入 `WaitMessage`，不再生成 ImGui/DX11 帧，并提示 Windows 整理工作集；快捷键、托盘和 OLE 消息仍可唤醒线程。
- 图标加载接口接收目标像素尺寸：程序资源使用 `PrivateExtractIconsW`，系统关联图标使用对应尺寸的 Shell 图像列表。

## 10. 所有权与错误处理

- COM 和 DX11 对象使用适当的 RAII 智能指针管理。
- Win32 句柄使用小型、专用的所有权封装，不建立通用万能句柄框架。
- 可恢复错误通过结果对象返回，并带有供日志/界面使用的上下文。
- 启动失败、单个图标失败或单个无效条目不应导致整个应用退出。
- 初始化关键步骤失败时，应清理已创建资源并给出明确错误。
- 首版不引入异常作为跨模块的主要控制流，具体错误类型随实现逐步确定。

## 11. 性能边界

- 不进行全盘扫描、索引或后台网络活动。
- 启动时只读取必要配置和首屏所需资源。
- 图标纹理按需创建并使用有界缓存。
- 不使用后台线程，除非测量证明同步操作明显阻塞界面且任务边界清晰。
- 不以复杂缓存换取未经测量的微小收益。
- 阶段 1 起记录冷启动、工作集和空闲 CPU，后续优化以数据为依据。

## 12. 目录迁移策略

目标目录按模块建立，但不在当前阶段移动模板文件。后续采用增量迁移：

1. 先建立最小 `app`、`platform` 和 `renderer` 文件，使窗口与渲染循环工作。
2. 再引入 `core` 和 `config`，形成只读原型。
3. 最后加入 `ui` 的编辑能力和测试。

每次迁移都同步更新 `.vcxproj` 与 `.vcxproj.filters`，并保持工程可编译。不会为了目录整齐一次性重写入口文件。

## 13. 明确不采用的设计

- 插件接口、动态模块发现或脚本运行时
- 服务定位器、依赖注入容器或事件总线
- 数据库、ORM 或后台索引器
- 跨平台抽象层
- 网络客户端、遥测或账号基础设施
- 以搜索框为中心的命令系统
- 将界面改为侧边栏或资源管理器布局
